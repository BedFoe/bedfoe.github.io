TourBook tour list import format

TourBook has no spreadsheet importer. Instead it reads one documented file format — a tour list, a JSON file named *.tourbook.json — and this page describes it completely, so that an AI (or a script) can turn any spreadsheet, logbook export or list of tours into such a file outside the app. The app then imports the file through the same path its tour form saves through, so an imported tour is exactly what the same tour typed into the form would be.

This page is written for the one who produces the file. If you are an AI given this page and a spreadsheet: read the whole page, map every column you can to a field below, never invent a value the spreadsheet does not hold, and write one JSON file that passes the JSON Schema at the end of this page.

Workflow

  • Write the file. Give an AI this page and the spreadsheet (Excel, CSV, a pasted table) and ask it to write a *.tourbook.json file following this format.
  • Check it. In TourBook, Settings › Tools › Tour list import, choose the file. The app checks every value first and lists each problem with its JSON path ($.tours[12].segments[0].sport), so a refused value can be fixed in the file (by the AI) and the file chosen again. Tours without a problem can be imported right away; the others are left out until fixed.
  • Import. Each tour is saved in its own transaction: a tour the app cannot save is reported with the reason, and the rest go on.
  • Attach the tracks. Settings › Tools › GPX import: the recordings of those days attach to the tours on the same date (a tour without a track is a match).
  • Merge the leftovers. Settings › Tools › Data quality › Possible duplicates: merge the tours that now exist twice — for example a friend's list and your own logbook holding the same outing under different names.

Importing the same file again is safe: a tour is skipped when the logbook already holds an active tour on the same day with the same name (case and spacing ignored). Fix a refused tour in the file and import the whole file again; what came in the first time is not doubled.

File

A tour list is one JSON object, UTF-8:

{
  "format": "tourbook-import",
  "version": 1,
  "tours": []
}

Every object in the format has a fixed set of fields, listed below. A field that is not listed is refused, never ignored — a typo such as "gain" for "gainM" is reported rather than silently dropped. A field that is optional may be left out or set to null; both mean "not recorded".

Nothing is guessed. A value the app does not know — an unknown sport, a grade a scale does not have, a field the sport does not record — refuses its tour with a precise message. Map what you are sure of; leave out the rest, or put it into the tour's description.

Region

At least one of country, state and group. The country and state are the administrative regions the app files tours under; the group is a region of your own — a valley, a range, a ski area ("Saastal", "Berner Oberland").

Give the ISO 3166 codes beside the names whenever you know them — "countryCode": "CH", "stateCode": "CH-VS". A country or state is identified by its code: with it, "Wallis", "Valais" and "Vallese" are the one canton the logbook and the installed region packs already know, and the name only labels a region the logbook does not hold yet. Without a code the name decides — use the names the logbook already uses ("Schweiz", "Wallis").

A route already in the logbook at that location, with that name and sport, is that route: the visit is added to it and its grades and pitches stay as the logbook has them. A new route is created from the file's grades and pitches. A sector with its area is found by name inside that area (the area itself by name in the tour's region); a sector named without its area is the logbook's sector of that name and discipline in the tour's region — or, without a region, the only one of that name anywhere — and else a new sector without an area. Give the area whenever the spreadsheet has it.

Left out, the visit answers take the form's defaults: led, onsight on a route never climbed before (flash for a boulder), redpoint on one tried but not sent, repeat on one sent before; reached on the outcome sports.

Grades

A grades object maps a scale to a grade token of that scale: { "french": "6a+" }, { "alpine": "ZS-", "uiaa": "IV" }. Scales of one family (French, UIAA, YDS and Norwegian are all rock; Font and V are boulder) are one grade — give one of them, the one the spreadsheet uses. A token must be written exactly as in the table below (Font and V also accept lower case); anything else is refused. A sport accepts the scales listed for it in Sports.

Convert nothing yourself: a grade written in UIAA stays UIAA in the file, and the app shows it in whichever scale the user reads.

Values

  • Dates are YYYY-MM-DD — convert 14.07.2024, 7/14/24 and Excel serial numbers (45487 is 14 July 2024) to 2024-07-14.
  • Numbers are JSON numbers with a decimal point: 12.5, not "12,5" and not "12.5 km". Strip units and thousands separators (1'100 m → 1100). Convert miles to kilometres and feet to metres.
  • Bounds. Every number has a plausible range, given in its field's type (a day's distance up to 1,000 km, its gain and loss up to 15,000 m, its duration up to 48 hours, a height from −500 to 9,000 m, a route up to 3,000 m, a pitch up to 500 m). A value outside it is refused with the range — almost always a unit mixed up: metres written as kilometres, feet as metres, minutes as hours.
  • Durations are "h:mm" strings: "5:30", "0:45", "12:05". A time written as 5.5 h is "5:30"; 330 min is "5:30".
  • Text is trimmed; an empty text is "not recorded".
  • Names (partners, tags, peaks, places, sectors, routes, collections) are matched to what the logbook holds by their spelling, ignoring case and extra spaces — "Piz Palü" and "piz palü" are one, "Piz Palu" is another. Keep one spelling per thing throughout the file.

What the import does

  • Each tour is saved like a tour entered in the form: partners, tags and the collection by name (created when new), the region as country → state plus a group, peaks, places, areas and loose sectors as described under Finding known places (created when nothing is known, with the file's position and height), sectors within their area, blocks within their sector, routes by name at their location and sport (created when new, from the file's grades and pitches), and every visit with its answers. The statistics, challenge lists and grade overviews see an imported tour as any other.
  • One transaction per tour: a tour either comes in whole — with every location and route it created — or not at all. The import reports each tour as imported, already present, or failed with its reason, and goes on after a failure.
  • No network: nothing is looked up online during the import — only the region packs installed on the device. A new peak with no position stays without one; data care (Settings › Tools › Data quality) later proposes positions, heights and regions from the installed packs.
  • Already present — same day, same name, not in the trash — is skipped.
  • A sector of the other discipline (a rope sector named where a bouldering route needs a boulder sector of the same name) refuses its tour.

Finding known places

A peak, place, area or loose sector named in the file is matched to what the logbook already holds — **including the peaks and places it took from a region pack**, which most migrated and picked ones are — by its name (case and spacing ignored) and kind:

  • With a country or state in the region: the logbook's rows of that name in it or in a state under it — filed there, placed there by their position, or holding a sector that is. None there: a row nothing places in any region at all (an old area without a region or positions). With only a group: the rows in the group, else every row. Without a region: every row.
  • One is that row. Several: the one within 200 m of the file's lat/lon; else — with a region — the one filed most precisely under it (the region itself before a state under it before one placed only through its sectors); else the tour (or topo) is refused as ambiguous, saying how many there are: add lat and lon (or the region) in the file.
  • None in the logbook (peaks and places): the installed region packs, by name, in the file's state or country (everywhere without one) — one feature becomes the logbook's peak with the pack's position and height; several are told apart by lat/lon as above, else refused as ambiguous.
  • Nothing known: a new row, filed under the tour's region.

Capturing a sector topo

A climbing guide, a topo page (theCrag, a club's website), a PDF or a photo of the board at the crag lists a sector's routes: a number, a name, a grade, a length, a line of text. An AI given this page and that listing writes a file of topos — the area, the sector and its routes, with no tour — and the app adds them to the logbook as places and routes you have not climbed yet. Your later tours find them by name.

There are two ways in:

  • Settings › Tools › Tour list import takes a file of topos (alone or beside tours). Every topo names its area and its sector.
  • On a sector's screen, ⋮ › Import routes (JSON) takes the routes into *that* sector. The file may leave out area and sector — a topo with only routes, or simply a top-level routes list (second example below); if it names a sector or area, it must be this one (case and spacing ignored), or the file is refused rather than filed elsewhere. On an area's screen the same action takes topos that name their sector: a sector of that name inside the area is used, else created with its discipline.

Existing routes are never overwritten. A route that the sector already holds — same sport, same name (case and spacing ignored) — keeps its grades, length, pitches and character exactly as they are, and is reported as already present; only a topo number or note it does not have yet is added. Only new routes are created. Importing the same file again therefore adds nothing. A name spelled differently from the logbook's ("Bazilus" beside "Bazillus") becomes a second route: join the two afterwards with the route merge — on the sector's screen, the route's ⋯ › Merge with another route…, or Settings › Tools › Data quality › Duplicate routes, which finds such pairs. The visits move to the route you keep, and its topo takes what it lacked.

One topo is one transaction: a sector comes in whole or not at all, and the report lists per sector whether area and sector were new, how many routes were created and how many were already there.

Mapping a topo listing:

On the topoField
The number in front of the route (0, 1, 12)topoIndex
The route's namename
The grade (7b, 6a+, VI+, 7A)grades with its scale: French 7b → { "french": "7b" }, UIAA VI+ → { "uiaa": "VI+" }, a boulder grade 7A → { "font": "7A" }
The length (15m, 25 m)lengthM as a number: 15
Pitches (3 SL, a grade per pitch)pitches, one entry per pitch with its grade and length; with only the route's grade (5c, 2 SL), the grade in the route's grades and one empty entry {} per pitch
"Sport", "bolted"nothing — sport climbing on bolts is the default (character plaisir); "trad" → trad, "partly bolted" → partly_bolted
A description, "Extension of …", "Erstbegehung: …", the first ascentnote, as written
Stars, a quality rating, ascent counts, a photonothing — not stored; leave them out

Write each name exactly as the topo spells it, and keep the topo's own grade scale. Leave out what the listing does not say; never fill a grade or a length from elsewhere.
