TourBook archive format

Your logbook belongs to you. Every backup TourBook writes is an ordinary ZIP file that holds an ordinary SQLite database, your photos and files as they are, and your GPS tracks in a small binary format described below. Standard tools read all of it: any unzip program, the sqlite3 command-line shell or a database browser, and a few lines of code for the tracks. TourBook does not need to be installed to get your data back out.

This page describes format version 2, written by TourBook 1.0 and later.

The file

A backup is named tourbook-backup-YYYYMMDD-HHMMSS.tbx.zip, an export of selected tours tourbook-export-YYYYMMDD-HHMMSS.tbx.zip. The time is UTC. Both are plain ZIP archives (no ZIP64, so at most 4 GiB). Photos and other already-compressed files are stored as they are, everything else is compressed with Deflate.

Path in the archiveWhat it holds
db/tourbook.dbThe SQLite database: tours, segments, places, routes, ascents, partners, tags, collections, the track figures.
media/<year>/<tourId>/<mediaId>.<ext>A tour's photo or file. Beside it <mediaId>.thumb.<ext> (a small preview) and, when the original was kept, <mediaId>.original.<ext>.
media/locations/<locationId>/<mediaId>.<ext>A photo of a place, sector or peak, with the same .thumb and .original companions.
gpx/<year>/<tourId>/<trackId>.tbgOne GPS track in the TBG1 format below.
gpx/<year>/<tourId>/<trackId>.gpxThe GPX file the track was imported from, when it was kept.
manifest.jsonWhat the archive holds, with a checksum for every file. It is written last, so an archive cut short has none.

<year> is the year of the tour's date. Every path below media/ and gpx/ is also stored in the database (media.rel_path, media.thumb_rel_path, gpx_track.geometry_rel_path, gpx_track.archive_rel_path), so each file belongs to exactly one row.

manifest.json

A JSON object with these fields:

FieldMeaning
formatVersion2 for this format.
sourceapp: written by the TourBook app.
appVersionThe app version that wrote the archive.
schemaVersionThe database's schema version, explained under Versions below.
createdAtWhen the archive was written, ISO 8601 in UTC.
contentsfull: the complete logbook of one installation, for a restore. filtered: selected tours, for importing into another logbook. Archives written before this field existed are full.
databaseIdAn identifier of the logbook, the same in all its full backups. Absent in a filtered export.
countsRows per table in the archived database: { "tour": 429, … }.
entriesEvery file of the archive except the manifest itself: { "path", "bytes", "sha256" }, with the uncompressed size and the SHA-256 of the uncompressed content as lowercase hex.
totalBytesThe sum of all entries[].bytes.

counts covers these tables: person, region, tag, collection, location, location_attribute, route, route_pitch, route_grade, route_pitch_grade, tour, tour_segment, tour_person, tour_tag, tour_location, segment_grade, ascent, ascent_pitch, media, gpx_track, gpx_waypoint. Tours in the trash are counted too.

To check an archive by hand: unzip it and compare sha256sum of each file with its entry.

The database

db/tourbook.db is a regular SQLite 3 database, not encrypted. Its own schema is the reference: sqlite3 tourbook.db .schema lists every table, column and rule with comments. The tables that hold your logbook:

TableWhat a row is
tourOne outing: date (date_from, YYYY-MM-DD), name, description, region, collection. deleted_at is set while the tour is in the trash.
tour_segmentOne sport within a tour, in order (sort_index): the sport, the typed distance, height gain and loss, duration, and a race result where there was one.
tour_person, tour_tagThe partners and tags of a tour (person, tag).
tour_locationThe peaks and places of a tour. role is summit (reached), attempt (turned back) or visited.
locationA peak, place, climbing area, sector or boulder, with position and height. parent_id builds the tree: area, then sector, then boulder.
route, route_pitch, route_grade, route_pitch_gradeA route at a location with its pitches and grades. A route belongs to its location, not to a tour.
ascent, ascent_pitchOne visit of a route on a tour segment: style, role (lead, follow, alternating), number of goes, the pitches climbed.
segment_gradeThe difficulty of a segment per grading scale, typed or derived from its ascents.
gpx_track, gpx_waypointA recorded track of a segment (its file is the .tbg) and its waypoints.
tour_gpx_metrics, segment_gpx_metricsFigures computed from the tracks: distance, gains, times, paces, speeds.
mediaA photo or file of a tour or of a location.
collectionA named group of tours, with an optional planned span.
regionA region tree (country, canton, …).
segment_condition, segment_attribute*Conditions such as snow or avalanche level, and the attributes you defined yourself.

The other tables describe the app's own state on the device (settings, backup history, installed map packs, the migration log) or are the vocabularies below.

Stored values are stable English keys, never translated text: a sport is hiking, ski_touring, climbing; an ascent style onsight, redpoint; a location kind peak, sector. Every vocabulary is a table of its own whose rows are the allowed keys: sport, enum_location_kind, enum_ascent_style, enum_ascent_role, enum_difficulty_scale, enum_route_character, enum_tour_location_role, condition_value. A grade is stored as written on its scale (route_grade.scale = french, value = 6b+), with ord as its position on that scale for sorting.

Units are in the column name: _m metres (gain_m, elevation_m, length_m), _s whole seconds (duration_s), _km kilometres, _kmh km/h, _mh metres per hour, size_bytes bytes. Positions are WGS 84 degrees (lat, lon). Times are ISO 8601 text. A missing value is NULL, never 0. Identifiers are UUIDs (version 7) as text.

Tracks: the TBG1 format

A .tbg file holds one track as columns of fixed-size numbers, all little-endian:

OffsetSizeField
04The ASCII characters TBG1.
42Flags (unsigned): bit 0 = the track has heights, bit 1 = the track has times.
62Reserved, 0.
84count: the number of points (unsigned).
124t0: the earliest time, seconds since 1970-01-01 UTC (unsigned); 0 without times.
164 × countLatitudes: signed 32-bit, degrees × 10 000 000.
…4 × countLongitudes: signed 32-bit, degrees × 10 000 000.
…4 × countOnly with bit 1: seconds after t0, unsigned 32-bit.
…2 × countOnly with bit 0: height in whole metres, signed 16-bit; −32768 means no height for that point.

Times are all or nothing: a track has a time for every point or for none. The columns follow each other without gaps; the file ends after the last one. A recording with several track segments is one track.

This JavaScript turns a .tbg into points and into a GPX file. It needs no library and runs in Node or a browser:

function readTbg(bytes) {
  const view = new DataView(bytes.buffer, bytes.byteOffset, bytes.byteLength);
  const magic = String.fromCharCode(...bytes.subarray(0, 4));
  if (magic !== 'TBG1') throw new Error('not a TBG1 track');
  const flags = view.getUint16(4, true);
  const count = view.getUint32(8, true);
  const t0 = view.getUint32(12, true);
  const hasHeight = (flags & 1) !== 0;
  const hasTime = (flags & 2) !== 0;
  const latAt = 16;
  const lonAt = latAt + 4 * count;
  const timeAt = lonAt + 4 * count;
  const heightAt = timeAt + (hasTime ? 4 * count : 0);
  const points = [];
  for (let i = 0; i < count; i++) {
    const height = hasHeight ? view.getInt16(heightAt + 2 * i, true) : -32768;
    points.push({
      lat: view.getInt32(latAt + 4 * i, true) / 1e7,
      lon: view.getInt32(lonAt + 4 * i, true) / 1e7,
      ele: height === -32768 ? null : height,
      time: hasTime ? new Date((t0 + view.getUint32(timeAt + 4 * i, true)) * 1000) : null,
    });
  }
  return points;
}

function tbgToGpx(bytes, name = 'Track') {
  const escape = (text) => text.replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;');
  const points = readTbg(bytes).map((p) => {
    const ele = p.ele === null ? '' : `<ele>${p.ele}</ele>`;
    const time = p.time === null ? '' : `<time>${p.time.toISOString()}</time>`;
    return `<trkpt lat="${p.lat}" lon="${p.lon}">${ele}${time}</trkpt>`;
  });
  return [
    '<?xml version="1.0" encoding="UTF-8"?>',
    '<gpx version="1.1" creator="tbgToGpx" xmlns="http://www.topografix.com/GPX/1/1">',
    `<trk><name>${escape(name)}</name><trkseg>`,
    ...points,
    '</trkseg></trk>',
    '</gpx>',
  ].join('\n');
}

In Node, fs.writeFileSync('track.gpx', tbgToGpx(fs.readFileSync('track.tbg'))) writes the GPX next to it. The track's name, sport and tour are in the database: gpx_track.geometry_rel_path names the file, gpx_track.tour_segment_id its segment.

Versions

formatVersion changes only when the container itself changes. The database changes more often: every app update that changes a table raises schemaVersion. Version 1.0 starts at schemaVersion 49. TourBook restores an archive from any earlier version since then and brings its database up to date while doing so; it refuses an archive written by a newer app than itself, and one written by a test version before 1.0 (schemaVersion below 49). An export of selected tours is imported only by an app at the same schemaVersion. Your copy of an older archive always stays readable with the tools above, since every version is a plain SQLite database.
